# UdpFileTransfer

UdpFileTransfer は、**通信できる方向が一方向しかない環境でもファイルを転送するための Java 8 CLI ツール**です。

通常のファイル転送が用いるACK、NACK、自動再送などを使わず、送信側から受信側へのUDP通信だけで転送します。欠落したデータは受信側の `missing` で確認し、利用者が電話、チャット、別ネットワークなどで番号を送信側へ伝えて個別再送します。

## 仕組み

1回の送信起動では、送信側がランダムな128 bitのセッションIDを生成します。メタデータと全データパケットに同じIDを付け、受信側は**最初に受理したメタデータ**のセッションIDをその受信処理中は固定します。その後に届く別セッションのパケットは現在のファイルへ混入させません。

ただし、セッションIDは送信者認証や事前共有された転送指定ではありません。受信側は最初に受理可能なメタデータを採用するため、待受UDPポートへ到達できる第三者が先に有効なメタデータを送れば、その転送が採用され得ます。`recv --expected-session` のような機能はありません。必要な送信元制限はOS、ファイアウォール、ネットワーク構成で行ってください。

メタデータには次を含めます。

- セッションID
- 送信元ファイル名
- 元ファイルサイズ
- チャンクサイズ
- チャンク総数 (`chunkCount`)
- 元ファイル全体のSHA-256

送信元ファイル名はUTF-8で最大1024 bytesです。受信側はシーケンス番号からファイル内の位置を求めるため、順不同で受信できます。同じシーケンス番号を再度受信した場合は、最初に正常に書き込んだ内容を維持します。

受信データは最終出力へ直接書かず、`<output-file>.part` に再構成します。必要な全データが揃った後にファイルサイズとSHA-256を検証し、**両方が一致した場合だけ `.part` を最終出力へ置換して `receive completed` になります。**

## ダウンロード

正式な配布物は [GitHub Releases](https://github.com/rhktrth/UdpFileTransfer/releases) から取得します。通常は最新Releaseの `UdpFileTransfer-<version>.zip` を使用してください。

## 必要環境

- Java 8 以上

配布ZIPを展開し、`UdpFileTransfer.jar` を使用します。

## 受信

受信側を先に起動します。

```text
java -jar UdpFileTransfer.jar recv <output-file> [-p <port>] [-n <max-chunks>]
```

例:

```text
java -jar UdpFileTransfer.jar recv recv.bin -p 30070 -n 300000
```

既定値:

- port: `30070`
- max chunks: `300000`

`-n` は1転送で受け入れる最大チャンク数を指定します。上限を超えるメタデータは採用せず、**既存の最終出力と `.part` を変更しません**。この上限は、受信済みシーケンスの状態量と1転送あたりのUDPデータグラム数を直接制限するものです。

ファイルサイズそのものの独立した上限はありません。受信できるファイルサイズはチャンクサイズと最大チャンク数の組合せで決まります。既定の300,000チャンクでは、既定チャンクサイズ700 bytesなら約200 MiB、プロトコル上限9972 bytesなら約2.99 GB（約2.79 GiB）が目安になります。

受信中のコマンド:

```text
missing
```

sequence `0` から最大1,000個の位置を確認し、未到着番号を表示します。空改行も同じです。後続範囲がある場合は `next: missing <開始番号>` が表示されます。

```text
missing 1000
```

指定sequenceから最大1,000個を確認します。

```text
quit
```

受信を中止して正常終了します。途中までの `.part` は自動削除しません。既存の最終出力は変更しません。

### SHA-256不一致からの復旧

全データ受信後にファイルサイズまたはSHA-256が一致しない場合、受信はエラーで終了し、`receive completed` は表示しません。最終出力は置換せず、不一致の `.part` を残します。

復旧するときは、送信元ファイルが転送中に変更されていないか、誤ったパケットを送っていないかなどを確認し、受信側の `recv` を再起動してから、送信側で `all` を実行してメタデータと全チャンクを再送してください。新たな有効メタデータを採用すると、残っている `.part` は切り詰められ、受信状態を最初から作り直します。

## 送信

```text
java -jar UdpFileTransfer.jar send <input-file> [-h <host>] [-p <port>] [-c <chunk-size>] [-i <interval-ms>]
```

例:

```text
java -jar UdpFileTransfer.jar send send.bin -h 192.0.2.10 -p 30070 -c 700 -i 0
```

既定値:

- host: `127.0.0.1`
- port: `30070`
- chunk size: `700` bytes
- interval: `0` ms

chunk sizeは `1..9972` bytesです。`9972` はUFT1上の上限であり、ネットワーク上の推奨値ではありません。大きいUDPデータグラムはIPフラグメンテーションを起こし、経路によって損失しやすくなる可能性があります。通常は既定値700を起点にしてください。

送信側は対話コマンド受付前に入力ファイルサイズとSHA-256を計算します。**送信プロセスを起動してから転送を終えるまで入力ファイルを変更しないでください。** ファイルサイズの変化は送信側でも検出し、同じサイズの内容変更も受信側のSHA-256検証で正常完了しません。

送信中のコマンド:

```text
all
```

同一セッションのメタデータを2回送信した後、全データチャンクをsequence順に送信します。空改行も同じです。

```text
meta
```

メタデータだけを1回再送します。

```text
4352
```

sequence `4352` のデータチャンクだけを再送します。

```text
quit
```

正常終了します。

## 転送手順

1. 受信側を `recv` で起動する。
2. 送信側を `send` で起動する。
3. 送信側で `all` を実行する。
4. 受信側が終了しなければ `missing` で未到着番号を確認する。
5. 必要なsequence番号を別経路で送信側へ伝え、個別再送する。
6. 受信側が `receive completed` になるまで必要に応じて繰り返す。

## UFT1 とセキュリティ

現在のUFT1は開発中の通信形式です。識別子は `UFT1` のまま仕様変更することがあり、旧開発版とのwire互換性は保証しません。CLIの旧 `-s` / `-m` オプションも互換維持しません。

セッションIDは採用済み転送を取り違えないためのランダム識別子です。SHA-256は受信ファイルとメタデータの内容一致を確認します。ただし、**送信者認証、認可、暗号化、MAC、電子署名は提供しません**。メタデータとデータの双方を書き換えられる攻撃者に対して真正性を保証するものではありません。

UDP待受ポートは用途に応じてOS、ファイアウォール、ネットワーク構成で隔離・制御してください。

詳細仕様は [外部設計書](https://github.com/rhktrth/UdpFileTransfer/blob/main/docs/EXTERNAL_DESIGN.md)、内部設計は [内部設計書](https://github.com/rhktrth/UdpFileTransfer/blob/main/docs/INTERNAL_DESIGN.md) を参照してください。
