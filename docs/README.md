# UdpFileTransfer ドキュメント構成

このディレクトリには、UdpFileTransfer を仕様駆動で変更するための設計文書を置きます。仕様IDやテストとの追跡可能性は維持しつつ、設計書そのものは人間が上から読んで理解できることを優先します。

## 1. 文書体系

| 文書 | 主な役割 |
| --- | --- |
| [`../README.md`](../README.md) | 利用者向けの概要、導入方法、基本操作 |
| [`EXTERNAL_DESIGN.md`](EXTERNAL_DESIGN.md) | コマンドライン、通信、ファイル、表示、エラーなど、外部から確認できる仕様 |
| [`INTERNAL_DESIGN.md`](INTERNAL_DESIGN.md) | 全体構成、クラス責務、処理方式、状態、並行処理、リソース管理などの内部設計 |
| [`OPERATIONS.md`](OPERATIONS.md) | ビルド、テスト、配布物作成、リリースの手順 |
| [`adr/`](adr/) | 重要な設計判断、採用理由、見直し条件 |
| [`../AGENTS.md`](../AGENTS.md) | AI や開発者が文書と実装を変更する際の作業規則 |

外部仕様と内部設計がソースコードやテストと矛盾する場合、コードの現状だけを理由に仕様を決め直してはなりません。どの動作を正とするかを明示的に判断し、正本となる設計書から修正します。

## 2. 設計書の書き方

### 2.1 人間が読む順序を優先する

設計書は仕様ID順、クラス名順、テスト名順には並べません。目的、全体像、インターフェースまたは内部構成、主要処理、状態、異常系、制約、受入条件という自然な順序を基本とします。仕様IDは該当する設計内容の近くに付けます。

### 2.2 日本語を基本とする

本文、章名、節名、表見出しは原則として自然な日本語で記述します。意味のある理由なく英単語をそのまま並べる書き方は避けます。

ただし、識別子や標準的な技術名称として原文を維持する方が正確なものはそのまま記載します。

- コマンド名: `send`, `recv`, `all`, `missing`, `quit`
- クラス名・メソッド名: `UdpFileReceiver`, `receive()`, `close()`
- プロトコル上の値や項目名: `UFT1`, `chunkSize`, `chunkCount`, `sessionId`
- Java API: `DatagramChannel`, `FileChannel`, `ByteBuffer`
- 例外型や終了時の実際の表示文字列

英語の識別子を使う場合も、その意味は日本語で説明します。ADRも同じ日本語方針に従います。

### 2.3 外部設計と内部設計を分ける

外部設計には、実装方式を変更しても利用者や通信相手から確認できる契約を書きます。主な対象はCLI、対話コマンド、UDP通信、UFT1、順不同・重複・欠損の扱い、ファイルの確定条件、表示、終了コード、セキュリティ境界です。

内部設計には、外部仕様を安定して実現するために維持すべき責務、状態、処理方式、並行処理、リソース所有、不変条件を書きます。補助メソッド名や単なる処理分割は、設計上の意味がない限り固定しません。

## 3. 仕様駆動開発の進め方

機能や動作を変更するときは、原則として次の順で進めます。

```text
Issue / 要求
    ↓
EXTERNAL_DESIGN.md と外部仕様
    ↓
受入条件 AC-*
    ↓
INTERNAL_DESIGN.md / 必要な ADR
    ↓
テスト
    ↓
製品コード
    ↓
README / OPERATIONS
```

実装を先に変更し、その実装を正当化するために設計書を後から書き換える進め方はしません。内部設計を検討して外部仕様が不適切と分かった場合は、実装へ合わせて黙って変更せず、外部設計へ戻って判断を明示します。

## 4. 仕様ID

| 種別 | 形式 | 例 |
| --- | --- | --- |
| 外部仕様 | `EXT-<AREA>-NNN` | `EXT-WIRE-004` |
| 内部設計 | `INT-<AREA>-NNN` | `INT-LIMIT-001` |
| 受入条件 | `AC-<AREA>-NNN` | `AC-CLI-001` |
| 未決事項 | `TBD-NNN` | `TBD-003` |
| 設計判断記録 | `NNNN-<name>` | `0003-sequence-addressed-idempotent-reconstruction` |

主な区分は `ENV`, `CLI`, `NET`, `WIRE`, `SEND`, `RECV`, `FILE`, `OBS`, `SEC`, `CMP`, `LIFE`, `CONC`, `ERR`, `LIMIT` です。仕様IDは章立ての代わりではありません。

## 5. 受入条件と追跡可能性

`AC-*` は、重要な外部仕様を実装詳細に依存せず確認するための条件です。「前提」「操作」「外部から確認できる結果」が分かる形にします。

重要な変更では、少なくとも次を追跡できる状態にします。

```text
外部仕様 EXT-*
    ↓
受入条件 AC-*
    ↓
内部設計 INT-*
    ↓
テスト
    ↓
製品コード
```

すべてを1対1に対応させる必要はありません。

## 6. 既存コードから設計を復元する場合

1. README、既存設計、ADR、テスト、製品コードを相互に確認する。
2. 利用者、通信相手、ファイル、標準出力、終了コードなどから観測でき、互換性維持に意味があるものだけを外部仕様にする。
3. 責務、状態、リソースの寿命、並行処理など、実装を安定して変更するために必要なものだけを内部設計にする。
4. 偶然そう実装されているだけの補助処理や定数は、設計上の意味がない限り固定しない。
5. 文書と実装が矛盾する場合は推測で片方を正とせず、Issue や PR で判断を明示してから正本を更新する。

不明な事項は推測で埋めず、必要に応じて `TBD-*` として明示します。

## 7. 完了条件

- 外部動作が変わる場合、対応する外部仕様と受入条件が先に更新されている。
- 内部構造を変える場合、維持すべき設計が内部設計へ反映されている。
- 重要な選択に代替案や明確な理由がある場合、ADR が更新されている。
- 受入条件を確認するテストが存在し、対応関係を追跡できる。
- 設計書とADRは自然な日本語で、人間が上から読んで理解できる。
- ソースコードの偶然の実装詳細を不要に仕様化していない。
- README、運用手順、設計書、テスト、製品コードの間に説明できない矛盾がない。
