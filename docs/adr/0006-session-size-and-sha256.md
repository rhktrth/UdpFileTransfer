# ADR-0006: UFT1にセッションID、ファイルサイズ、SHA-256を含め、検証後に出力を確定する

## 決定

UFT1の通信形式に次を含めます。

- 全パケット共通の128 bitセッションID
- メタデータの元ファイルサイズ
- メタデータの元ファイル全体SHA-256

セッションIDは1回の送信プロセス初期化時に `SecureRandom` で16 bytes生成し、メタデータと全データパケットで同じ値を使用します。受信側は採用したメタデータと異なるセッションIDのパケットを破棄します。

SHA-256は32 bytesの生値としてメタデータへ格納します。受信側は全データを `<output>.part` へ受信した後、ファイルサイズとSHA-256を検証し、両方が一致した場合だけ `.part` を最終出力へ置換します。

ファイルサイズをメタデータへ持たせ、`chunkCount` と各sequenceの期待payload長をファイルサイズから検証します。これにより最終データ長も一意になります。

送信元ファイル名はUTF-8で最大1024 bytesとし、メタデータ全体を最大1108 bytesへ抑えます。UFT1全体のUDPデータグラム上限10000 bytesは維持します。

受信側のリソース制限はファイルサイズではなく `maxChunkCount` で行い、既定値を300,000とします。この値は受信側CLIで変更できます。

本リポジトリはまだ開発中で外部互換性を確約していないため、wire format識別子は `UFT1` のまま更新し、旧開発版との後方互換処理は追加しません。

## 理由

シーケンスだけでデータを識別すると、前回転送の遅延パケットや別送信プロセスのパケットが同じポートへ到着した際に、別ファイルのデータを現在の転送へ混入させる危険があります。ランダムな128 bitセッションIDを全パケットへ付けることで、片方向通信のまま採用済み転送を分離できます。

元ファイルサイズがなければ、最終パケットの正確な長さを受信側が決定できません。ファイルサイズを持たせることで、チャンク数と全payload長を検証できます。

全シーケンスが形式上そろっただけでは内容の一致を確認できません。SHA-256を完成後に確認することで、パケット混在、破損、送信中の元ファイル変更などによる内容不一致を正常完了から除外できます。

さらに、未検証データを最終出力へ直接書くと、受信途中やSHA-256不一致でも既存の正常ファイルを破壊します。`.part` へ受信して検証後に置換することで、正常完了の境界をファイルシステム上でも明確にします。

受信側の状態量と必要データグラム数はファイルサイズではなく `chunkCount` に直接比例します。このため、リソース制限も `chunkCount` に適用する方が目的に合います。

## 結果

- UFT1のdata headerは28 bytes、最大payloadは9972 bytesです。
- 旧開発版UFT1とのwire互換は保証しません。
- session IDは認証ではなく、採用後の転送を分離する識別子です。
- SHA-256はmetadataに対する認証を提供しません。
- 送信側初期化時にファイル全体を1回読み、SHA-256を計算します。
- 受信側は全データ受信後に `.part` を1回読み直してSHA-256を計算します。
- 検証失敗時は既存の最終出力を維持し、`.part` を残します。
- 再実行時は新たな有効メタデータ採用後に `.part` を切り詰め、転送を最初からやり直します。
- 受信可能なチャンク数を増やす場合は利用者が `-n` を明示的に増やします。
- 将来、送信者認証や改ざん耐性が必要になった場合は、MACまたは電子署名を含む別の設計判断が必要です。
