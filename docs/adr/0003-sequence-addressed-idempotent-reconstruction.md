# ADR-0003: シーケンス番号を論理ファイル位置として扱い、順不同・重複受信を許容する

## 決定

ファイルは固定のチャンクサイズで分け、各データパケットに0始まりのシーケンス番号を付けます。受信側は次の式で書き込み位置を決定します。

```text
offset = chunkSize * sequence
```

メタデータの `fileSize` と `chunkSize` から `chunkCount` と各シーケンスの期待データ長を一意に決定し、通信で受け取った値との整合性を確認します。

受信側は未到着番号を全件事前生成せず、正常に `.part` へ書き込めたシーケンスだけを受信済み集合へ追加します。欠損は `0..chunkCount-1` と受信済み集合との差分として必要時に導出します。

同じシーケンスを複数回受信した場合は、最初に正常書き込みが完了した内容を採用し、後続を無視します。到着順はファイル再構成の条件にしません。

受信側は `maxChunkCount` を設け、既定値を300,000とします。この値はCLIで変更できます。

## 理由

UDPでは欠落、順序入れ替わり、重複が起こり得ます。また、UdpFileTransferでは欠損したデータだけを利用者が個別再送できる必要があります。

シーケンス番号をファイル上の論理位置として扱えば、各パケットを他の到着状況に依存せず直接配置できます。`fileSize` を持つことで最終パケット長も一意に決まり、短すぎる・長すぎる最終データを正常扱いしません。

受信済みシーケンスだけを保持しても、その要素数と必要なデータグラム数は `chunkCount` に比例します。ファイルサイズ上限では、小さいチャンクサイズを指定した場合の状態数を直接制限できません。そこで、受信側が実際に管理する `chunkCount` 自体へ上限を設けます。

## 結果

- ファイル全体をメモリへ保持せず、位置指定書き込みで再構成できます。
- 到着順をそろえるバッファは不要です。
- 重複受信しても最初に正常書き込みした内容を維持します。
- 最終データ長を含め、各シーケンスの期待長は `fileSize` から検証します。
- 受信側は必要なリソース量に応じて `maxChunkCount` を変更できます。
- ファイルサイズそのものの独立した受信上限は持ちません。
