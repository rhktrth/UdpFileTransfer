# ADR-0005: 並行処理を対話入力に限定し、プロセスのライフサイクルをCLIが所有する

## 決定

送信側の初期化と送信操作は同期処理とします。入力ファイル、宛先の名前解決、ファイルチャネル、UDPチャネルを初期化できない場合は、その失敗を呼び出し元へ返し、対話コマンド受付へ進みません。

受信側も呼び出し元スレッドで同期的にブロッキングUDP受信を実行します。対話CLIと受信を並行させるため、受信モードではコマンド入力だけをデーモンスレッドとして実行します。受信側の `close()` は UDP チャネルを閉じてブロッキング受信を解除します。

受信側は転送完了時にもI/O失敗時にも `System.exit` を呼びません。正常完了は `receive()` のreturn、I/O失敗は `IOException` として呼び出し元へ返し、JVMの終了と終了コードはCLIが決定します。

複数スレッドから実際に参照される受信済みシーケンス、受信件数、終了状態だけを必要な範囲でスレッド安全に扱います。

## 理由

送信側は継続的なバックグラウンド処理ではなく、利用者のコマンドに応じて同期的にパケットを生成・送信するだけです。初期化だけを非同期化すると、呼び出し元が成功・失敗を確定できないままコマンド受付へ進み、未初期化状態を扱う危険が生じます。

受信側もUDP受信自体を別スレッドへ移す必要はありません。必要なのはブロッキング受信中にも利用者が `missing` や `quit` を入力できることだけなので、対話入力側を1本のデーモンスレッドに分離すれば要件を満たします。

プロセス終了を受信処理内部に持たせると、受信側単体のテストや同一JVM内での利用が難しくなります。CLIへライフサイクルの責務を集約することで、内部処理とプロセス方針を分離できます。

## 結果

- 送信側コンストラクタの成功後は送信可能状態であることを前提にできます。
- 送信側用の作業スレッド、初期化完了シグナル、キューは不要です。
- 受信側は呼び出し元スレッドで同期実行し、受信モードの追加スレッドはコマンド入力用1本だけです。
- 受信側のブロッキングI/Oは `close()` によって解除可能でなければなりません。
- 受信側内部からプロセスを強制終了しません。
- 受信側のI/O失敗は `IOException` として呼び出し元へ返します。
- 並行処理用の仕組みは、実際に複数スレッドから共有される状態に限定します。
